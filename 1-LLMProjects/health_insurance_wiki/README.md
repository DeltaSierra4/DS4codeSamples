# health-insurance-wiki

Seven skills that build and maintain a knowledge base of health insurance plans, so that
questions like *"which of these is cheapest for someone with a chronic condition"* get
answered from stored, sourced facts rather than by re-reading a stack of PDFs every time.

The knowledge base is plain markdown on disk. Nothing is indexed into a vector store,
nothing needs a server, and nothing needs a pip install — the retrieval layer is the
directory layout, and it is designed so that one subagent can become the master of one
carrier without ever reading another carrier's pages.

---

## The skills

| Skill | What it does |
|---|---|
| `/hiw-setup` | Scaffolds the wiki: five directories, the page contract, the operating rules, the config. Creates no carrier and no plan — an empty `companies/` is the correct end state. |
| `/hiw-ingest` | Reads plan details out of files (PDF, DOCX, TXT, XLSX, PPTX, HTML) or a carrier URL and writes them as structured plan pages, one company folder per carrier. The engine; everything else reads what it writes. |
| `/hiw-refresh` | Re-fetches the sources already on record, diffs them against what is stored, reports rate changes, and goes after the fields still reading `TBD`. |
| `/hiw-list-plan` | Builds `output/plan-catalog.html` — every plan, grouped by carrier, sortable and filterable. Fans out one subagent per carrier for the narrative. |
| `/hiw-query` | An interactive needs assessment, then a ranked recommendation. Fans out one subagent per carrier to find that carrier's best matches. |
| `/hiw-compare` | A side-by-side matrix of two or more plans with three annual-cost scenarios, computed in Python rather than by a language model. |
| `/hiw-lint` | Health-checks the wiki, auto-repairs the unambiguous, marks contradictions for a human, and regenerates `index.md`. Runs interactively or on a schedule. |

Set up once, ingest repeatedly, lint after every handful of ingests, and query or compare
whenever. That order is a recommendation, not a requirement — every skill is standalone
and reports a degraded path rather than blocking.

## What the wiki looks like on disk

```
<wiki-root>/
├── SCHEMA.md              the page contract, copied in at setup, never edited in place
├── AGENTS.md              how to retrieve from and write to this wiki
├── CLAUDE.md              a pointer plus the current state summary
├── index.md               every plan, grouped by company (regenerated by /hiw-lint)
├── log.md                 append-only, every skill writes here
├── _config/
│   └── wiki-config.md     currency, plan year, geography, cost-model assumptions
├── companies/
│   └── <company-slug>/
│       ├── company.md         carrier overview + plan roster
│       ├── plans/
│       │   └── <plan-slug>.md one page per plan, per plan year
│       └── sources/
│           └── <slug>.md      one receipt per ingested document or URL
├── raw/<company-slug>/    immutable originals
├── synthesis/             saved comparisons and recommendations
└── output/                generated HTML and reports
```

## The three ideas that make it work

**The company folder is the unit of parallelism.** Everything a subagent needs to answer
a question about one carrier is inside `companies/<slug>/` and nowhere else. No plan's
facts live outside its own company folder, and no company's page depends on another
company's page. That is why the fan-out is safe: a per-carrier subagent has a naturally
bounded context and *cannot* contaminate one carrier's facts with another's. The
directory layout is the parallelism plan.

**`TBD` over a guess, and `TBD` is never a zero.** A cost the source did not state is
written as the literal `TBD`. It renders as `TBD` in every catalog and every comparison,
it sorts last in every ascending sort, and a cost scenario that needs it is reported as
*not computable* with the missing input named — never estimated with the term dropped. A
fabricated deductible is worse than an absent one, because `/hiw-compare` will rank on
it and nothing downstream can tell it from a number read off an SBC.

**One walker, many consumers.** `lint-wiki.py` is the only thing that walks the tree. It
emits one JSON document carrying both the plan inventory and the findings, and
`index-wiki.py`, `patch-wiki.py`, `build-catalog.py` and `build-comparison.py` all read
that JSON. Four scripts that never disagree about what the wiki contains.

A fourth, smaller one: **ingest resolves; lint flags.** `/hiw-ingest` and `/hiw-refresh`
settle a conflict at write time and log the decision. `/hiw-lint` marks what it cannot
decide and never picks a winner. Stated on both sides, in the same words, so neither
skill drifts into the other's job.

And a rule that follows from all of them: **every derived artifact has exactly one
writer.** `index.md` is `/hiw-lint`'s, wholesale — nothing else patches it, and a stale
index is a normal condition rather than an error. `companies/` is written only by ingest
and refresh. `synthesis/` only by query and compare. Nothing generated ever lands inside
a company folder, because company folders hold sourced facts only.

## Installing

### As a plugin

```
/plugin marketplace add <path-to>/wiki_v2
/plugin install health-insurance-wiki@wikiwiki
```

`.claude-plugin/plugin.json` declares all seven skills; `marketplace.json` wraps the
directory as a one-plugin marketplace. Skills resolve their own scripts via
`$CLAUDE_PLUGIN_ROOT`, so this works from wherever the plugin lands.

### As plain skills

Copy the seven directories into a `skills/` folder — either `~/.claude/skills/` for
everywhere, or `<project>/.claude/skills/` for one project:

```bash
cp -r wiki_v2/skills/hiw-* ~/.claude/skills/
```

Every `SKILL.md` resolves its own files with a two-rung ladder — `skills/<name>/scripts/`
first, then `$CLAUDE_PLUGIN_ROOT/skills/<name>/scripts/`, and `assets/` in place of
`scripts/` for `hiw-setup` — so the same file works installed either way, with no edit.
Three skills reach into a sibling's `scripts/` by the same ladder, because
`lint-wiki.py` is the family's single tree walker and duplicating it would mean two
walkers that eventually disagree.

### Requirements

Python 3.8 or later, and nothing else. Every script is standard library only: no
PyYAML, no jinja, no requests, no openpyxl. That is deliberate — an ingest skill that
needs a pip install is an ingest skill that fails on a locked-down laptop.

`pdftotext` (poppler-utils) is used for PDFs **if it happens to be on PATH**. Where it is
not, `extract-source.py` exits 2 and tells the agent to read the PDF with its own native
reader rather than returning partial text. A plausible mis-extraction of a benefits table
is worse than no extraction, because either way the number lands in the wiki.

## The scripts

| Script | Lives with | Role |
|---|---|---|
| `lint-wiki.py` | `hiw-lint` | the only detector and the only tree walker. Read-only. Emits inventory + findings as one JSON, with a stable `rule` id, a `severity` and an `autofix` flag per finding |
| `patch-wiki.py` | `hiw-lint` | the only writer of page fixes. Consumes `autofix: true` findings, re-detects nothing, and refuses any rewrite that would not preserve the value |
| `index-wiki.py` | `hiw-lint` | regenerates `index.md` from the JSON. Never walks the tree |
| `build-catalog.py` | `hiw-list-plan` | joins the JSON to the subagents' narrative on `plan_id`; emits one self-contained HTML file |
| `build-comparison.py` | `hiw-compare` | resolves plan ids, computes three annual-cost scenarios, ranks over the plans that record each field. `--json` emits the computed totals, which is how `/hiw-query` reads them rather than scraping the HTML |
| `extract-source.py` | `hiw-ingest` | plain text out of docx/xlsx/pptx/html/txt/csv/json via `zipfile` + XML. Exit 2 means "read it natively" |
| `new-page.py` | `hiw-ingest` | emits a schema-conformant plan, company or source skeleton. Refuses to overwrite (exit 3) |

All seven are invoked by path and never inlined, retyped or regenerated. The shipped file
is the single source of truth for what gets detected and what gets computed; an edited
copy changes the result while still appearing to work.

Every one takes `--help`. Exit codes are `0` on success and `1` on a hard error, plus two
documented extras that are not failures: `extract-source.py` exits **2** for "this format
needs your own reader", and `new-page.py` exits **3** for "that page already exists, read
it instead". **Findings never affect the exit code** — a wiki with 400 violations still
exits 0, because the JSON is the report and the skill flow does not branch on `$?`.

Output conventions differ by what each script produces, and deliberately:

| Script | stdout | stderr |
|---|---|---|
| `lint-wiki.py`, `patch-wiki.py` | the JSON payload, unless `--out` is given | a one-line receipt |
| `build-comparison.py` | the JSON payload with `--json -`; `--list` prints a plan-id table | a one-line receipt |
| `index-wiki.py` | the markdown with `--out -` | a one-line receipt |
| `build-catalog.py` | nothing — HTML goes to `--out` | a one-line receipt |
| `extract-source.py` | the extracted text, unless `--out` is given | notes and warnings |
| `new-page.py` | the page with `--print` | a one-line receipt |

So `lint-wiki.py --wiki . | jq` works unconditionally, and stderr never contaminates a
machine payload.

## The cost model

`/hiw-compare` computes three annual scenarios. They live in
`build-comparison.py` — forty readable lines — rather than in a prompt, because an LLM
asked to add a premium, a deductible and four copays will usually get it right and will
occasionally not, and there is no way to tell which run you got.

| Scenario | What it assumes |
|---|---|
| **Healthy year** | 12 × premium + N primary-care copays + N months of tier-1 generic. Nothing touches the deductible. Illustrative. |
| **Moderate year** | 12 × premium + the full individual deductible + N specialist copays + one imaging study + N months of tier-1 generic. Illustrative, and the softest of the three. |
| **Bad year** | 12 × premium + the individual out-of-pocket maximum. **Exact**, not illustrative — in-network the OOP max is the ceiling on everything except premium, so this is the true worst-case annual exposure. |

The visit counts are tunable via `cost_model_*` keys in `_config/wiki-config.md`, and
they are **printed on every deliverable whether or not you have changed them**. An
assumption a reader cannot see or change is indistinguishable from a fabricated number.

The most useful thing the three scenarios produce is the **crossover** — the point where
the ranking flips. A Bronze plan that wins the healthy year and the bad year while losing
the moderate year is the whole story of that comparison, and it is invisible to anyone
skimming a single column.

## What this is not

A structured record of what published sources say about health insurance plans. Not a
quoting engine, not an eligibility determination, and not advice. Premiums stored here
are list values for a stated basis and will differ from what a specific person is offered
once age, ZIP code, tobacco use, household size and subsidy eligibility are applied.
Every deliverable carries that caveat visibly, and no skill removes it. Coverage
decisions rest on the carrier's official plan documents.

## Lineage

The architecture comes from two earlier skill families in this repository. `wiki_v0`
(`ddv-wiki-*`) contributed the LLM-as-librarian pattern: raw sources in, structured
interlinked pages out, an append-only log, and a self-contained HTML site built by a
stdlib Python script. `wiki_v1` (`int-bpsi-*`) contributed the discipline: a page
contract copied byte-for-byte and cited by section number, the resolve/flag split between
ingest and upkeep, the four-tier finding model that reduces an approval gate to one
question, the fan-out spec written as threshold → partition key → enumerated return
contract → hard barrier, and the practice of ending every `SKILL.md` with an
anti-patterns list that grows a bullet each time something breaks.

What is new here: the company folder as the explicit unit of parallelism, `TBD` as a
first-class non-value carried all the way to the DOM, stable `rule` ids with severity and
autofix flags on every finding, a patcher that independently re-verifies value
preservation before writing, and deterministic cost modelling with TBD propagation.
